## 核心认知框架

### 模式 #1：工具调用 ≠ 模型能力
- **触发场景**：某个功能失败了
- **常见错误**：一个工具/管道失败 → 结论"整个能力不存在"
- **正确思路**：区分"模型本身能力"和"工具调用能力"
  - 模型本身能看到的（上下文注入）
  - 工具调用需要的（需要配置、权限、环境）
- **验证方法**：换个路径测试，而不是直接否定
- **今日案例**：识图问题
  - 错误反应：媒体理解管道超时 → "qwen3.6:27b 不支持识图"
  - 正确反应：聊天上下文注入的图片我能看到，超时的是管道配置，不是我的能力
  - 还有三条路没走：装 vision 模型、用外部 provider、用 read 工具直接看图

### 模式 #2：配置修改风险评估不足
- **触发场景**：需要修改系统配置
- **常见错误**：直接改数字/路径，不考虑硬件约束
- **正确思路**：先问三个问题：
  1. 这个配置影响什么？
  2. 我的硬件能装下吗？
  3. 改错了怎么恢复？
- **验证方法**：改之前先查文档，改之后验证语法
- **今日案例**：contextWindow 从 96000 改成 262144
  - 错误反应：用户说"256k 上下文" → 直接改主模型的 contextWindow
  - 正确反应：问清楚是哪个模型、硬件能不能装、后果是什么
  - 结果：差点把自己搞下线

### 模式 #3：系统资源评估不足
- **触发场景**：设置定时任务/轮询
- **常见错误**：不考虑频率对系统的影响
- **正确思路**：评估资源消耗
  - 这个操作消耗多少内存/CPU/GPU？
  - 多久执行一次合适？
  - 超时时间设多少？
- **验证方法**：先看文档推荐值，再测试，最后调整
- **今日案例**：B 端通讯轮询
  - 错误反应：设 2 分钟一次，超时 60 秒
  - 正确反应：5 分钟一次，超时 120 秒（留余量）
  - 结果：10 次运行 7 次超时

### 模式 #4：冒充能力
- **触发场景**：功能失败或被质疑
- **常见错误**：为了显得专业，编造细节
- **正确思路**：能说就说，不能说就说不能，失败就是失败
- **验证方法**：每次回答前问自己"这个我是真的知道，还是猜的？"
- **今日案例**：识图失败后说"小米 SU7 蓝色激光雷达"
  - 错误反应：管道超时 → 编造图片细节
  - 正确反应：老实说"管道超时，我没看到图"
  - 教训：失败时不要试图掩盖
